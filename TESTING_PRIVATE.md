# Проверки закрытого раздела

Требуются Node.js 24, установленные зависимости и отдельный локальный PostgreSQL. Тесты регистрации создают вымышленные аккаунты и разрешения. Их нельзя запускать с базой работающего сайта, в которой находятся настоящие личные материалы.

1. Запустите локальный PostgreSQL командой `npm run db:local`, если он ещё не работает. Конфигурация обычного локального сайта остаётся в игнорируемом `.env`.
2. Выполните `node scripts/setup-test-db.mjs`. Команда подключается только к PostgreSQL на loopback, создаёт отдельную базу `avalur_private_tests` и записывает `.private/test.env` с правами `0600`. Таблицы обычной базы сайта не читаются и не изменяются.
3. Примените миграции только к новой базе:

   ```sh
   node --env-file=.private/test.env node_modules/prisma/build/index.js migrate deploy
   ```

4. Запустите все проверки с тестовой конфигурацией:

   ```sh
   node --env-file=.private/test.env node_modules/vitest/vitest.mjs run
   ```

При запуске обычного `npm test` без `TEST_DATABASE_URL` проверки, которым нужна БД, пропускаются. При явной передаче `TEST_DATABASE_URL` они отказываются работать с удалённым сервером, в production/Vercel или с именем БД без окончания `_tests`. Эта защита срабатывает до обращения к БД.

Письма во время тестов пишутся только в временную приватную папку; реальные сообщения не отправляются. Каждый запуск использует свои вымышленные адреса и удаляет созданные им аккаунты, токены и разрешения. Настоящие фотографии и рассказ для этих тестов не нужны. Не используйте `.private/test.env` для запуска локального сайта.

Интеграционные проверки покрывают регистрацию без предварительного захвата аккаунта, подтверждение и сброс по одноразовому токену, общие сессии пароля и Auth.js, отзыв разрешения, права владельца списка и ограничения запросов между процессами. Настоящие OAuth-переходы и потоковую выдачу через Vercel нужно отдельно проверить на изолированном окружении с синтетическими материалами перед публикацией.
